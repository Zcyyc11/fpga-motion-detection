## 一、阻塞级

### 1. `multi_bbox.v` —— 资源爆炸王（bit 产出阻塞）

- **现象**：模块进真实综合即整设计超限，`place_design` 必失败，bitstream 永远无法生成。
- **实锤**：综合后 Slice LUT = **96,997 / 53,200（182.33%）**；层级报告中 multi_bbox 独占 **83,286 LUT（占全部 86%）**；对照单目标基线仅 10,605 LUT（19.93%）。
- **根因**：16 标签并查集 + 16×16 游程全并联匹配，`find_root` 是**带循环的函数还被 16 路并行调用** → 16×16 指针追逐 mux 链；查根/合并/更新全塞在游程关闭的那一拍（阻塞赋值区）内完成。
- **治本要求**：流水化重写——游程关闭事件几十拍才发生一次，完全够分步算；`find_root` 改小状态机或限深；16 路并联比较改单比较器分时复用；**接口不变**（遵守接口冻结表），16 目标能力保留，**LUT 压到 50%（26,600）以下并留余量**。
- **参考**：Appiah, Hunter, Dickinson, Owens. *A run-length based connected component algorithm for FPGA implementation*. FPT 2008. DOI: 10.1109/FPT.2008.4762381（游程编码 + BRAM 架构，实时且低资源，本问题的标准解法）。亦可评估"只要包围盒不要标签"的 blob bounding-box 专用架构，比通用 CCL 更省。
- **应急**（今天上板等不起时二选一，需线一在群内拍板）：① 用已实测 PASS 的单目标 HDMI bit（`board_top_hdmiin.bit`，WNS 0.932）先上板，保"真实硬件跑通"硬门槛；② `MAX_LABEL`/`MAX_RUN` 由 16 临时砍到 4（并联网络平方级缩水，现有 tb 只测 2 目标仍能过）——动算法核心，须你确认后重跑仿真。

### 2. `track.v` —— 同款坏模式（结构实锤，量级待测）

- **实锤**（代码亲读）：整模块只有一个 always 块（L78 起），帧边界（`frame_tick`）一拍内用阻塞赋值完成：16×16 贪心最近邻匹配（L110-145 双层 for，`MAX_TRACK=16 × MAX_TARGET=16`）+ 轨迹表压缩更新（L147-168）+ 输出列表生成。与 multi_bbox 完全同一个"一拍算完"坏模式。
- **精度修正**：层级报告前五中**没有** track.v，所以它实际占多少 LUT 未经实测——治本时同批改，改完重新综合看数，别凭断言下结论。
- **治本要求**：匹配与表压缩拆拍/流水；阻塞赋值区重构为标准时序逻辑；行为不变（跨帧 id、dwell、MISSED_MAX=5 老化）。

## 二、治本级（随第 1 项同批做）

### 3. `alarm.v` —— 中低优先级 + 一个真功能隐患

- **实锤**：`MAX_ID=256` 的 `seen[]`/`prev_cx[]`（L40-41）复位时 for 循环清全表（L50-52），复位树巨大；每拍 `t_id` 直接索引 256 深表（L61-72）。量级估计仅几百 LUT，不是问题源。
- **改进**：复位只清必要位 / 标记位惰性初始化；索引结构换更省实现。
- 🔴 **真功能隐患（与 track 叠加）**：track 的 id 为 8bit（255 回绕不回收）→ 回绕后 alarm 的 `seen[t_id]` 误判"新 id"→ `prev_cx` 被重置 → **穿越检测可能漏报**。修 3 时请一并处理此场景（这是仿真测不出来的路径，tb 要补）。

### 4. `overlay_multi.v` —— 实锤但低优先级（线一认账，本人编写）

- **问题①**：双缓冲在 `f_edge` 一拍全量拷贝 16 目标 × 5 字段（L94-97）→ 正确做法是**乒乓指针切换**（改指针不拷数据），一拍完成且零 FF 浪费。
- **问题②**：画框组合逻辑对每个像素串行比较 16 个目标框（L122-124）→ 可按目标区间裁剪 / 分块预判。
- **精度修正**：该模块总共仅 **769 LUT**，两条都实锤但都不是问题源，顺手改、不当重点。

### 5. `overlay.v` —— 死代码（不是"两套并存"）

- **实锤**：`md_pipeline.v` 只例化 `overlay_multi`（`u_ovm`），`board_top.v` 与全部仿真台均无 `overlay.v` 引用 → 已是**没人用的死代码**（构建 glob 会编译但不例化，综合直接优化掉，零成本）。
- **处置**：确认无引用后删除或移入归档目录；不存在"参数化合并"的必要。

## 三、测试与工程（线一补充）

### 6. 仿真强度不足（资源问题漏网的帮凶）

- `tb_multi_bbox` **只测 2 个目标**——无 16 目标打满、无游程超限（MAX_RUN）、无标签表满、无 id 回绕用例。multi_bbox 从未进过真实综合，雷就是这么埋下的。
- **要求**：治本后补齐上述用例，特别是 16 目标满配 + 跨帧合并路径。
- **另发现**：`tb_gray_conv` 按线二新版 gray_conv 接口编写（in_de/in_hsync/in_vsync/in_rgb），而构建实际使用 `board/gray_conv.v` 旧接口（vde/x/y/pix_in）→ 该 tb 当前**测的是 rtl_pending 备用版而非部署版**，仿真链对不上部署实现。两版取舍归线二拍板后，tb 必须与部署版对齐（全套仿真 9/10 通过的例外即此条）。

### 7. dvi2rgb IP 树残留 ILA 孤儿（工程卫生）

- 项目生成目录里躺着 `ila_pixclk`/`ila_refclk` 两个 ILA（当年按 Digilent zybo-z7-10 参考流程定制 IP 时插入的，打包板型错配）。已核实：**wrapper 未例化，不进综合、不吃资源**；但 `.xci` 写 `kDebug=false` 与残留文件矛盾。
- **处置**：下次重置/重新生成工程时干净重定制 dvi2rgb（不带 debug），无需紧急处理。
