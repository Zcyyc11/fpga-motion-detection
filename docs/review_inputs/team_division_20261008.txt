二、三个人怎么分：三条线并行
最重要的一条：不是 A 做完 B 才能做。 三条线同时开跑，只在「接口」上碰面。
为什么能这样？因为模块之间的约定本来就很瘦 —— 每两级之间只有几根线（位宽、有效信号、坐标）。内部怎么实现，别人完全不需要知道。
线一 · 视频通路与上板
需要什么：板子 + HDMI 显示设备 + Vivado
干什么：
HDMI 输入侧打通：摄像头画面 → 转灰度 → 接进现有流水线
参数控制：把阈值、警戒线做成寄存器，PS 侧 Python 能改
上板实测：真实画面跑通，记录帧率、延迟、稳定性
录制演示视频
交付：能跑的真实视频链路 + 实测记录 + 演示视频
为什么这条最重：它是「算法 → 产品」的最后一段，也是官方最看重的「板上实测」。
线二 · 算法与 PL 落地
需要什么：Vivado。★ 不需要 HDMI —— 写代码、跑仿真都不需要看画面。
干什么：
★ 把多目标检测、跟踪、越界告警从电脑搬进 PL（现在只在电脑上）
灰度模块（接 HDMI 输入要用，BT.601 整数近似，不难）
参数控制寄存器（跟线一对接）
报警规则细化（多区域、多规则）
算法实验台继续迭代
交付：PL 里的多目标/跟踪/告警 + 仿真证据 + 资源与时序报告
线三 · 验证、证据与纠错
需要什么：★ 只要一台电脑。不需要板子，不需要 HDMI。
干什么：
★ 独立复核：在你自己的机器上，复现我们报出来的数字（跑 algo_lab.py、cdnet_official.py）
★ 非 HDMI 验证通路：把结果从板子回传到电脑（串口/网口），用 Python 把框画出来
材料纠错（已经在做，那份 18 条清单质量很高，继续）
测试表格汇总、报告初稿
交付：复现记录 + 报告初稿 + 纠错清单
为什么这条必须有：★ 写的人不许给自己签字。你在另一台机器上复现，比我们自己说一百遍都管用。

四、不撞车的唯一办法：接口先冻结
三个人同时改代码，最怕的不是活多，是两个人改同一个文件、互相覆盖。所以下面这四处「接口」先定死。改任何一处，必须在群里说一声并得到确认。
#
接口
内容
I1
视频流总线
时钟 / 数据有效 / 行场同步 / 像素坐标 / RGB 位宽与极性
I2
大像素域
10 bit（2×2 求和）、640×360。★ 阈值是「和域」的，别拿单像素灰阶的直觉设数
I3
目标元数据
每个目标的左上右下坐标 + 编号 + 有效标志
I4
寄存器表
阈值 / 相对阈值 / 背景学习率 / 警戒线 / 停留时间 / 使能 的地址与复位值

完整定义在仓库 docs/接口冻结表.md。
★ 为什么必须这样：我们队的第一个杀手不是「活难」，是「顶层被两个人同时改」。顶层文件（md_pipeline.v）只有一个 owner，其他人只能提建议。
五、协作规矩
GitHub 怎么用：
main 分支是受保护的，不许直接往上推
每人一条自己的分支，改完提 Pull Request，至少一个人 review 过才能合
★ Vivado 工程目录不要提交（几百 MB，GitHub 单文件上限 100 MB）。只提交源码 + 约束 + Tcl 构建脚本
★ 不许在微信里口头改位宽——聊天记录不是接口文档。要改就提 PR 改接口表

换手验（我们只有三个人，不设专职测试，改成互验）：
你提交自己的模块前，必须由另外一个人跑一遍你的测试并回帖结论
★ 写的人不许给自己签字。 这是唯一的硬要求

三道硬门（过不了不能合并）：
仿真跑通，波形跟你声称的一致
综合资源与最高频率没有倒退
改过接口的，寄存器表同步改了

七、四个坑
★ 别只看 1~2 条序列的分数就下结论。我们有过血的教训：某个改动在 3 条快测里最好，一跑全量 12 条直接崩到 0.554。下结论必须跑全量。
别一上来学 HLS 或深度学习。比赛初级组考察的是逻辑设计、状态机、时序约束 —— 手写流水线是得分点，不是偷懒。
别刷视频不做事。看一节就在电脑或板子上敲一遍，否则等于没看。
别自己改接口。改之前先在群里说，这是三个人不打架的唯一保证。
