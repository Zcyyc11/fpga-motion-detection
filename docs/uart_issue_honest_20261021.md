# 串口回收未过 · 如实交代与原因分析（线一 2026-10-21）

## 现象（实测，不粉饰）
- 韦博 16 目标版 `ce621313` 上板跑通：视频全亮、16 目标红框稳定出（vehicles 32% / people-walking 12% / market-square 0.15%，多轮复现）。
- 但 PL UART 回传（PMOD A1/Y18）**一个字节都没收到**：CH340 COM6 能正常打开，`uart_receiver` 5 秒 idle 超时、`bytes_saved=0`（多轮复现，非偶发）。

## 已排除（有依据）
- COM / 模块 / USB / 驱动：COM6 能开、换过新 CH340 模块、pyserial 正常。
- 板子在跑：DGL 屏激活、采集 100% 亮帧、红框出——检测链确实在工作。
- 接线：按官方脚位（RXD→脚1/Y18、GND→脚5/11、VCC 悬空），且换过新模块。
- bit 本身：ce621313 哈希卡口 + 工程实查（INPUT_SEL=1 + multi_bbox MAX_LABEL=16），与"视频/检测正常"不矛盾。

## 可能原因（诚实排序；说明软件侧硬边界）
**软件侧边界（必须讲明）**：pyserial 只认"有效帧"，我能确认的是"COM6 0 字节 + 板子在跑"，但**无法用纯软件区分"片内根本没发" vs "发了但没接到 CH340"**。以下按嫌疑大小排序：

1. **【最大嫌疑】RTL：`frame_tick` 依赖 dvi2rgb vsync**
   `md_pipeline.v:308` `frame_tick = vs & ~vs_d`，其中 `vs` 是 dvi2rgb 恢复的 vsync；uart_tx 每帧靠 frame_tick 发帧头（`uart_tx.v` 状态机）。**而检测链（红框）靠"像素 y 回绕"判帧、根本不走 vsync**——所以"画面正常/红框出"并不代表"vsync 在翻"。若 dvi2rgb 的 vsync 输出没翻或有 glitch，`frame_tick` 不产生，uart 就一字节不发。这与"视频完美 + 串口死寂"的现象完全自洽，是当前第一嫌疑。

2. **RTL：uart_tx 输入驱动 / 时钟域**
   `BAUD_DIV=645` 是按 74.25MHz 推的；若 md_pipeline 实际时钟域/分频与预期不符，可能不发或乱码（但"0 字节"更倾向"根本没发"而非"发错"）。

3. **硬件：Y18→CH340 RXD 物理没通 / 没共地**
   线一坚称接线 OK，但软件侧无法 100% 证实 Y18 的电平真的到了 CH340 的 RXD（要证实需万用表测 Y18 / 示波器 / ILA）。

4. **硬件：CH340 模块电平跳线非 3.3V / TX-RX 直连帽残留**
   这类更常见是"乱码/丢包"，很少是"0 字节"，故嫌疑排最后。

## 结论与下一步（诚实）
- 主体（视频链路 + 16 目标检测 + 红框）**已实测通过**；串口是唯一未过项，且**不属于主体功能**。
- 纯软件已到头，要一锤定音需三选一：**ILA 抓 vs / frame_tick / uart_txd 波形**（看片内）、**万用表测 Y18**（看引脚发没发）、或**把 frame_tick 改成像素 y 回绕触发后复测**（既诊断又修复）。
- 今晚按线一指令暂不收口，如实记录在案，待改 frame_tick / ILA 验证后闭环。
