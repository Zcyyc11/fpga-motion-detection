## 记录 1-2｜`pyxrt.device(0)` 打不开设备：差点误判成权限问题

- **日期 / 编号**：2026-10-03 / 1-2
- **决策点**：串口命令行里跑 Python 加载 overlay 的程序，报
  `Could not open device with index '0'`，加 `sudo` 竟然**还是同样的错** —— 到底是不是权限问题？
- **提示词**：`【要点复述】`（情境：串口侧执行 Python 脚本失败，错误码指向 xrt 设备句柄，
  想确认是权限、驱动还是环境问题）
- **模型回答**：判断这**不是权限问题**，而是 PYNQ 3.1.1 的 XRT 运行环境依赖**环境变量注入**；
  `sudo` 会把当前环境清掉，所以加 sudo 无效甚至更糟。给出的做法：
  `source /etc/profile.d/pynq_venv.sh; source /etc/profile.d/xrt_setup.sh`，
  并用 `/usr/local/share/pynq-venv/bin/python3` 而不是 `sudo python3`。
  并说明 Jupyter 里不需要这么做。
- **我做了什么判断**：**采纳**。理由：模型解释与"加 sudo 无效"这一**反直觉现象**自洽 ——
  如果是权限问题，加 sudo 应该缓解；现象反而恶化，说明是**环境被清掉**，不是权限不够。
  这条解释能一次说通全部观察。
- **自我纠错轨迹**：
  - **我自己的第一反应就是错的** —— 看到 "Could not open device" 下意识认为要提权。
  - 关键转折：**加 sudo 后错误一模一样**，这个矛盾否掉了"权限"假设。
  - 按模型给的 source 两行执行 → 设备打开成功，overlay 加载返回 `OVERLAY_OK`、`ip_blocks = 21`。
  - 事后我把这条写成**铁律**（不是"注意事项"）：命令行跑代码**必须**先 source 这两个脚本，
  且**不要**用 sudo python3 —— 因为症状极易被误读成权限问题。
- **相关 commit**：无（属板卡环境操作，不进仓库）
- **是否 `#skill候选`**：✅ → `skill/pynq_overlay_bringup/`（"从哪些失败中总结"第 1 条）

## 记录 1-3｜烧卡"设备不出现"与"容量只剩 0.13 GB"

- **日期 / 编号**：2026-10-03 / 1-3
- **决策点**：两个现象都像是烧卡失败，需要判断到底是硬件问题、操作问题，还是正常现象。
- **提示词**：`【要点复述】`（情境：读卡器插上电脑后盘符不出现；换口重插后出现了，
  写完后 Windows 只显示一个 0.13 GB 的分区）
- **模型回答**：① 盘符不出现多半是**插入次序/枚举**问题，建议先插卡再插 USB、必要时换端口；
  ② 只显示 0.13 GB 是**正常**的 —— 镜像里还有一个 ext4 rootfs 分区 Windows 不认，
  判成功与否应看**卷标**与 **BOOT 分区内容**，而不是看总容量。
- **我做了什么判断**：**采纳**，并把它落成**具体可核验清单**：
  卷标是否变为 `PYNQ`；BOOT 分区是否含 `BOOT.BIN` / `image.ub` / `boot.py` / `boot.scr` / `REVISION`。
  实测这五项齐全，卷标已变 `PYNQ`，烧写耗时 05:37。
- **自我纠错轨迹**：
  - **我一度把"总容量对不上"当成烧写失败的证据** —— 这是错的。
  - 纠正依据：`E: PYNQ | 0.13 GB | FAT` 只是一个 FAT 引导分区，
    真正的 rootfs 是 ext4、Windows 看不见（开机后实测 rootfs 已自动扩到 14 G）。
  - 教训记下：**判据要选"能被独立验证的量"**（卷标、文件清单），
    而不是"看起来应该对得上的量"（容量）。
- **相关 commit**：无
- **是否 `#skill候选`**：✅ → `skill/pynq_overlay_bringup/`（"从哪些失败中总结"第 2、3 条）
