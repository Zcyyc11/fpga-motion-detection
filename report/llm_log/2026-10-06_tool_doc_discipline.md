# 大模型协作记录 · 工具与文档纪律（2026-10-06）

> **提示词栏的标注规则**：`【原文】`＝逐字原话；`【要点复述】`＝原始逐字记录未留存，

对交「大模型协作记录」这件事本身也有直接价值：**它证明我们知道"工具的返回"不等于"事实"**。

## 记录 5-1｜★ `doc_find_and_replace` 会**静默成功**：返回 ok 但一处没改

- **日期 / 编号**：2026-10-06 / 5-1
- **决策点**：改本地 `.docx`（计划表）里的文字，怎么确认**真的改上了**？
- **提示词**：`【要点复述】`（情境：用文档工具做查找替换，工具返回
  `{"message":"find_and_replace ok"}`，但回读文档内容发现**没有任何变化**）
- **模型回答**：指出 `old_text` 与文档实际文本不完全一致时（**哪怕只差一个空格**），
  工具会**照样返回成功但一处都不替换**；唯一可靠判据是看返回 JSON 里
  **有没有 `last_edit_index` 字段** —— **有＝真改了；没有＝一处都没匹配上**。
  并指出本项目那份 docx 里存在**大量双空格**（如 `8  项`、`等  microSD`），
  所以构造 `old_text` 必须先用查找接口拿到 `related_text` 核对空格数。
- **我做了什么判断**：**采纳，并把"看 `last_edit_index`"定为唯一判据**。
  之后改表格改用 `doc_set_table_cells`（本次返回的 `last_edit_index` 为 1449 / 4074）。
- **自我纠错轨迹**：
  - **错在哪**：我原先以"工具返回 ok"作为成功依据 —— 这类工具会**静默成功**。
  - 这属于**同型陷阱的第一次**：**工具的"成功"是它自己的说法，不是事实**。
  - 修正：所有对文档的写入，一律以**返回里的可核验字段**（`last_edit_index`）或**回读内容**为准。
- **相关 commit**：无（计划表 docx 不在仓库内）
- **是否 `#skill候选`**：✅ → `skill/video_pipeline_pitfalls/` 未收录（非 FPGA 领域），
  但作为**"工具返回 ≠ 事实"**的实例保留在本记录，并与 5-2、5-3 一起构成同一条判据的三次印证

## 记录 5-2｜★★ `editor_sdk` 改了没保存：**编辑器里的内容比磁盘新**

- **日期 / 编号**：2026-10-06 / 5-2
- **决策点**：计划表状态到底更新了没有？该信磁盘文件还是信编辑器？
- **提示词**：`【要点复述】`（情境：核对计划表时发现磁盘文件 mtime 停在 15:24、
  内容还是旧版（"唯一卡点：microSD 读卡器（已下单…）"），
  但编辑器里已经是新版（"原卡点已解决：…2026-10-03 到货…"））
- **模型回答**：（复盘）那段 10-06 的更新**只活在编辑器内存里，从未保存到磁盘**；
  走 `editor_sdk` 改本地文档，**改完必须显式保存**，否则关掉预览就丢。
  并且判断"文档现在长什么样"应**以编辑器为准**，不能只看磁盘。
- **我做了什么判断**：**采纳**。执行保存（18:07:12，文件从 31656 B 变为 32387 B），
  这一保存**同时把那段滞留内存的更新一并写回磁盘**。
- **自我纠错轨迹**：
  - **错在哪**：我先用磁盘 mtime 判断"计划表没更新"，差点把**编辑器里已经改好的内容重做一遍**。
  - 转折点：对**同一份文档**同时读磁盘与编辑器，两者内容不一致 → 才定位到"没保存"。
  - 修正并立规：① 改完**必须显式保存**；② **判断文档内容以编辑器为准**；
    ③ 保存后**回读确认**（体积/mtime/内容）。
  - 这条同时也是**同型陷阱的第二次**：**"看起来改了"与"真的改了"是两件事**。
- **相关 commit**：无
- **是否 `#skill候选`**：⬜ 属工具纪律，已进 MEMORY.md §九

## 记录 5-3｜★★ 同一文件一轮里发多处编辑会**互相覆盖**：`success ≠ 落盘`

- **日期 / 编号**：2026-10-06 / 5-3
- **决策点**：批量改同一个文件的多个位置，能不能一轮发完？
- **提示词**：`【要点复述】`（情境：同一轮里对 `pattern_gen.v` 发 3 处修改、
  对 `make_test_clip.py` 发 5 处修改，随后编译报
  `VRFC 10-2989 'X_MAX16' is not declared`）
- **模型回答**：（工具纪律）同一文件在一轮里发多处编辑，**各处会互相覆盖**，
  结果只活下来一部分；且**每处都返回 success**。唯一可靠办法是
  **同一个文件一次只发一处编辑，改完立刻回读**。
- **我做了什么判断**：**采纳，并写成硬规矩**：**同文件一次一处 Edit + 改完 Read 回读**。
- **自我纠错轨迹**：
  - **错在哪**：我把它当成"批量更高效" —— 实际是**每处都成功、但文件里只留一部分**。
  - **发现路径值得记**：`X_MAX16 is not declared` 这个错**不可能是逻辑问题**
    （该常量我刚加过）→ 只可能是"没写进去" → 于是**回读文件**，果然是丢了一处。
    **靠"这个错不该出现"反推出"工具没落盘"**。
  - 修正：逐条重发 + 每次回读确认 → 编译通过、仿真复跑 11/11。
  - 这是**同型陷阱的第三次**：**`success` 是工具的说法，不是文件的事实**。
- **相关 commit**：`82433ac`
- **是否 `#skill候选`**：⬜ 已进 MEMORY.md §九（"编辑纪律"）

## 记录 5-4｜文档结构：为什么改成"单权威 + 只写指针"

- **日期 / 编号**：2026-09-28 / 5-4
- **决策点**：文档太多、且同一件事在多个文件里各说一遍 → 容易读到哪个信哪个。
  怎么改才对"少出错、不健忘"友好？
- **提示词**：`【原文】` 用户：「文档过多既影响美观、你也老容易忘，怎么处理对你更友好？」
  → 拍板 `【原文】`「你认为如何让你效率高，不出错，不健忘就怎么做。去做吧」
- **模型回答**：指出根因**不是"文件多"，而是"同一件事多处在说"**：
  ① 重复源（README 的状态表 ↔ 计划表 docx）；② 按主题切而不按"要回答的问题"切 →
  单点问题要跨 6 份搜，搜不到就退回记忆里的旧摘要 → 出错；
  ③ **关键数字散落多处** → 版本漂移。
  给出的方案 = **两轴 + 一入口，不新增文件，只做收敛** + **关键数字只允许写在一处**。
- **我做了什么判断**：**采纳并执行**：
  - 三轴唯一权威：进度/产物 → 计划表 docx｜官方规则 → `竞赛规则与提交要求.md`｜
    技术决策 → `技术方案.md`；`README.md` 收窄为**唯一入口页**（删掉重复段落，只留现状 + 要求摘要 + 指路）
  - 每份文档顶部加一行「**权威范围**」（本文是 X 的唯一权威，Y 去别处看）
  - 被删内容逐条确认落点（**不丢信息**）：状态列→计划表；阶段出口判据→`技术方案.md` §六；
    L1/L2/L3 降级预案→**本轮搬入 `技术方案.md` §6.0**
- **自我纠错轨迹**：
  - 我先前的做法是"**再写一份更全的文档**"来解决"记不住" —— 方向**反了**，
    那只会增加重复源。
  - 转折点：把问题重新描述为"**同一件事只有一个权威源，其余只写指针**"。
  - 并按当时刚立的规矩做了**反向引用检查**（改结构后必 grep「谁指向我」）：
    grep 全库 `README|行动清单|还差什么` → 命中 **3 处失效引用，已修**。
  - 效果：README 256 行 → 约 230 行，但**结构性质变了** ——
    从"什么都讲一点"变成"只讲现状 + 要求摘要 + 指路"。
- **相关 commit**：无（资料库文档）
- **是否 `#skill候选`**：⬜ 属文档结构决策，已进 MEMORY.md §三 第 8 条

## 本轮小结

| 项 | 结果 |
|---|---|
| **同一条判据，三次印证** | **工具的"成功"不等于事实** —— ① doc 的 `find_and_replace` 静默成功 ② 编辑器改了没保存（编辑器比磁盘新） ③ 同文件多处编辑互相覆盖（`success ≠` 落盘） |
| 由此形成的方法 | 一律以**可核验字段**（`last_edit_index`）或**回读内容**为准；**同文件一次一处改 + 改完回读** |
| 文档结构 | 收敛为"**两轴 + 一入口**"；**关键数字只写一处**，别处只写指针；改结构后必做**反向引用检查** |
| 沉淀去向 | MEMORY.md §三（纪律）/ §九（踩坑速查）；本记录作为"纠错轨迹"留档 |
| 说明 | 本份记录**不建技能包** —— 与 FPGA/图像处理领域无关，对陌生队伍不可复用；但它证明本项目**对"工具报的成功"保持过怀疑并留下了判据** |
