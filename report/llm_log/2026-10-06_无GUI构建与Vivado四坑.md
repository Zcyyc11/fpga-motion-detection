## 记录 2-1｜Vivado 的 `file delete -force` 会在 batch 模式**永久卡死**

- **日期 / 编号**：2026-10-06 / 2-1
- **决策点**：每次构建要先清掉旧工程目录，这个清理放哪儿做？
- **提示词**：`【要点复述】`（情境：改掉 `close_project` 之后改成 tcl 里直接
  `file delete -force` 旧工程目录，结果整个构建 10 分钟毫无进展，需要判断是慢还是死）
- **模型回答**：给出**"假死"的判据与定位手法** —— 不看日志长度，而看
  **CPU 时间采样**：两次间隔采样 `tasklist /v`，若 CPU 时间数值完全相同、内存很小、
  窗口标题是 `OLEChannelWnd`，则说明它**在等一个隐藏的模态对话框**（batch 模式无人能点）。
  并给出对照实验：同一棵目录树用 OS 原生删除只要约 2 秒。
  结论：清理由**外层 `.bat` 的原生 `rmdir /s /q`** 做，Vivado 里一行删除都不留。
- **我做了什么判断**：**采纳**。理由：① 这个判据**可证伪**（有具体观测量：CPU 时间、内存、窗口标题）；
  ② 对照实验给了量化差距（10 分钟 vs 1.9 秒），足以排除"只是慢"；③ 把"删除"移出 Vivado
  是**结构性修复**，不是绕过。
- **自我纠错轨迹**：
  - **我先试的 `close_project` 是错的**：batch 模式下此刻没有打开的工程，
    它会抛 `ERROR [Common 17-53] No open project`，而 **`catch` 拦不住**，
    直接终止 Vivado（日志停在"旧工程目录已存在"，16 秒后 Exiting，exit 1）。
  - 于是**改成 `file delete -force`** —— 这第二个方案也错，就是我踩的最深的坑：
    碰到残留文件句柄时 Vivado 弹**隐藏模态框**，进程活着但永远等下去。
  - 现象记录（可复现）：主日志 10 分钟只长 0 字节；`tasklist /v` 两次采样（间隔 25 秒）
    CPU 时间都是 `0:00:43` 一动不动；内存 **15 MB**；窗口标题 **`OLEChannelWnd`**。
  - 修正：清理由 `.bat` 的原生 `rmdir /s /q` 做。改完重跑，
    主日志正常长到 5 万字节、两个 vivado 进程一个满载（20 秒里吃掉 19 秒 CPU）。
  - → 沉淀为**通用教训**：**别让 EDA 工具在 batch 模式下做可能弹窗的操作；
    "进程活着但没在算"用 CPU 时间采样一眼认出。**
- **相关 commit**：`98706ee`（feat(build) 可复现构建 + 报告 + bitstream）
- **是否 `#skill候选`**：✅ → `skill/report_autocollect/`（"从哪些失败中总结"第 1 条）

## 记录 2-2｜IP 的端口表是"配置决定"的，照文档抄一定错

- **日期 / 编号**：2026-10-06 / 2-2
- **决策点**：`board_top.v` 里要实例化 HDMI 发送 IP（`rgb2dvi`），端口怎么连？
- **提示词**：`【要点复述】`（情境：按"看起来应该有"的端口连了 `aRst_n` 与 `SerialClk`，
  综合直接报 `ERROR [Synth 8-11365] named port connection ... does not exist`）
- **模型回答**：判断这是**配置决定端口表**的典型问题，权威来源是 IP 生成目录里的
  `*_stub.v`（而不是文档、也不是记忆）。查 stub 后确认：当前配置下 `rgb2dvi_0` **一共只有 10 个端口**
  （`TMDS_Clk_p/n`、`TMDS_Data_p/n`、`aRst`、`vid_pData`、`vid_pVDE`、`vid_pHSync`、`vid_pVSync`、`PixelClk`）。
  两个"看起来该有"的端口之所以不存在：**`aRst_n` 只在 `kRstActiveHigh=false` 时才有**；
  **`SerialClk` 只在 `kGenerateSerialClk=false` 时才有**（该配置下 5× 时钟由 IP 内部自造）。
- **我做了什么判断**：**采纳**，并**删掉这两个连接**。理由：报错信息点名的就是这两个名字，
  而 stub 是工具根据**当前配置**生成的实际接口，优先级高于任何文档或印象。
- **自我纠错轨迹**：
  - **错因是我"凭印象补端口"**，不是 IP 有问题。
  - 定位方式：报错精确到行号（`board_top.v:99` / `:105`）+ 端口名 → 直接去读生成的
    `build/vivado/<proj>.gen/sources_1/ip/rgb2dvi_0/rgb2dvi_0_stub.v`，一眼看到真实端口表。
  - 修正后综合通过。失败日志时间戳：16:27:05 → 16:28:16。
  - 顺带把相邻的时钟约束也核了一遍：`kClkRange` 我原先填错（**填 3，应为 2**），
    依据是 IP 自带注释点名的 FVCO 约束（720p：`74.25 × 10 = 742.5 MHz`）。
    → 见技能包第 6 项。
  - → **写死教训**：调 IP 实例化前，先去看它**当前**生成的 stub/veo，别凭文档或记忆。
- **相关 commit**：`82433ac`（feat(rtl) 11 模块 + 板上层 + 引脚约束）、`98706ee`（构建脚本里的 IP 配置）
- **是否 `#skill候选`**：✅ → `skill/video_pipeline_pitfalls/` 第 7 条；`skill/mmcm_clock_search/` 第 2 条

## 记录 2-3｜`.bat` 光"纯 ASCII"不够，还必须 CRLF

- **日期 / 编号**：2026-10-06 / 2-3
- **决策点**：构建脚本跑起来"怪怪的"：似乎执行了两遍，还报莫名其妙的错。
- **提示词**：`【要点复述】`（情境：`.bat` 里报 `'n' 不是内部或外部命令`，
  且同一晚 16:15、16:19 各起了一次 Vivado —— 像是脚本被重复执行）
- **模型回答**：指出 **LF-only 行尾**会让 `cmd.exe` 解析错位，
  表现正是"脚本被重跑一遍"这类诡异现象；`cmd.exe` 按 GBK 读注释，
  所以 `.bat` 要 **纯 ASCII + CRLF 两样都对**；另外建议**去掉 `^` 折行续行**，
  每条命令写在一行，避免续行符在错位解析下吞掉下一条命令。
- **我做了什么判断**：**采纳**。理由：现象（重跑两遍 + `'n' 不是内部或外部命令`）
  与"行尾/续行解析错位"完全对得上，且改动是**机械可验证**的（改完看行尾、再跑一次看次数）。
- **自我纠错轨迹**：
  - 我原先只知道"`.bat` 要纯 ASCII"，**漏掉了 CRLF** —— 这是本次新增的一条。
  - 修正：两个 `.bat` 全部改为 CRLF，并去掉 `^` 续行。
    为防手改出错，写了一个修复脚本 `build/scripts/fix_bat_eol.py`。
  - 验证：重跑后只起**一次** Vivado，不再报 `'n' 不是内部或外部命令`。
  - → 沉淀为技能包第 5 项第 10 条。
- **相关 commit**：`98706ee`（build 目录下的 .bat 与修复脚本）
- **是否 `#skill候选`**：✅ → `skill/video_pipeline_pitfalls/` 第 10 条

## 记录 2-4｜★ 综合报"时序不收敛"，实现却是收敛的 —— 判据取哪个？

- **日期 / 编号**：2026-10-06 / 2-4
- **决策点**：`synth_timing_summary.rpt` 写着 **WHS = −0.466、8 个 hold 失败端点、
  "Timing constraints are not met"**；而 `impl_timing_summary.rpt` 是
  **WNS +0.695 / WHS +0.076、0 失败端点、"All user specified timing constraints are met"**。
  两个阶段结论相反，构建到底算不算通过？时序门该放在哪一步读？
- **提示词**：`【要点复述】`（情境：同一份设计，synth 报告写"未满足约束"，
  impl 报告写"全部满足"，需要判断谁是真的，并决定脚本里的时序门读哪一份）
- **模型回答**：两份报告的 `Design State` 不同 —— 一份是 `Synthesized`、一份是 `Routed`。
  失败端点集中在**跨 IP 内部时钟域**的路径上（`clk_pix_raw → PixelClkIO`，
  即 HDMI 发送 IP 内部时钟生成 → OSERDES 复位端）。综合阶段没有真实布线延迟，
  这类路径的估计偏悲观；布局布线后自然收敛。
  **结论：判时序只认实现阶段报告；时序门必须放在实现之后读。**
- **我做了什么判断**：**采纳**。理由：① 观察到的失败端点数在 impl 为 **0**，
  这是"物理上已经没有违规"的直接证据，不是解释；② `Design State` 字段给出了可区分的客观依据；
  ③ 我的构建脚本本来就把时序门写在 impl 之后，**与这个结论一致**，
  所以不需要改代码，只需要把"为什么"写清楚 —— 否则下次看到 synth 报告会白慌一场。
- **自我纠错轨迹**：
  - **我先看到的是 synth 报告**（`build/reports/synth_timing_summary.rpt`），
    一度以为构建其实没收敛、"exit 0"是假的。
  - 转折点：**去磁盘上核实物**，发现 `build/reports/` 里同时存在
    `impl_timing_summary.rpt`（18:03，`Routed`），其 Design Timing Summary 为
    `0.695 / 0.000 / 0 / 9978` 与 `0.076 / 0.000 / 0 / 9978`，并写明
    "All user specified timing constraints are met."
  - 于是修正判断：不是"构建撒谎"，而是**我把综合阶段的悲观估计当成了最终结论**。
  - 落地：① 报告与技能包里明确写"**判时序只认 impl 报告**"；
    ② 记下"失败端点全在 IP 内部跨域路径"这一特征，作为**区分"悲观估计"与"真实违规"**的依据。
- **相关 commit**：`98706ee`（报告产物 + 时序门位置）
- **是否 `#skill候选`**：✅ → `skill/report_autocollect/`（"从哪些失败中总结"第 4 条）
