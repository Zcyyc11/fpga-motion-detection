## 记录 4-1｜从"LD1 与 LD3 同步"反推出"白块不会绕回来"

- **日期 / 编号**：2026-10-06 / 4-1
- **决策点**：上板实测 LED 行为与预期不完全吻合，要不要当成硬件问题处理？
- **提示词**：`【原文】` 用户反馈：「要么同时亮，要么同时暗。」
- **模型回答**：解释这是**预期行为**，不是故障 ——
  `led[1] = b_valid`（本帧框有效）与 `led[3] = mask_seen`（本帧出现过运动掩码）
  本质是**同一个信息**（本帧有没有运动像素），所以必然同步。
  **但**顺着这个观察推下去会发现真问题：`pattern_gen.v` 里 `obj_x <= obj_x + DX16`
  **只有累加、没有回绕** → 白块 **1.3 秒出画 → 全黑 67 秒**（要等 16 位自然溢出才回来）。
- **我做了什么判断**：**采纳两层判断**：
  ① LED 同步＝正常，**不改**（避免把正常现象当 bug 改坏）；
  ② 白块不回绕＝**真问题，必须改** —— 因为接上 HDMI 后观众看到的是"闪一下然后一直黑"，
  会被误认为板子坏了，且演示视频无法录。
  并给出量化：720p 下 `X0=60`、`OBJ_W=160`、`DX=16` → 可见约 **77 帧 ≈ 1.28 s**；
  溢出后重新进来要 `(65535−1280)/16 ≈ 4016 帧 ≈ 66.9 s`。
- **自我纠错轨迹**：
  - **我原本只把 LED 异常当"待观察"**，没意识到它同时是"激励不会循环"的线索。
  - 转折点：把两个 LED 的语义摊开一看 —— 它们本来就同源，**没有异常**；
    真正异常的是"它们**一直亮着**"这件事本身，说明算法一直在检出运动 →
    说明白块**一直在动或一直没动**。顺着这条线算时序，就定位到了不回绕。
  - → 教训：**把"观察到的东西"先按语义拆开，再判断哪一条才是真线索。**
- **相关 commit**：无（诊断记录；修正见 4-2）
- **是否 `#skill候选`**：✅ → `skill/video_pipeline_pitfalls/` 第 9 条

## 记录 4-2｜回绕规则"三端同一行公式"

- **日期 / 编号**：2026-10-06 / 4-2
- **决策点**：回绕规则写在哪？三份文件各写一套，还是定一行公式三处照抄？
- **提示词**：`【原文】` 用户批准：「行。然后我今天新到了HDMI线。」
- **模型回答**：给出统一公式
  `x = (x + DX + OBJ_W > H_ACTIVE) ? X0 : x + DX`
  —— 即"**再走一步不会让右边缘越界就往前走，否则回到 X0**"，
  这样矩形**永远完整在画面内**，可以无限跑。并要求**三端照同一行写**：
  RTL（`pattern_gen.v`）、硬件模型（`rtl_golden.py::obj_x_at`）、PC 片段生成（`make_test_clip.py::x_at`）。
- **我做了什么判断**：**采纳，并在三份文件的头注释里都写"改一端必须同步改另一端"**。
  理由：这三份文件本来就是"同一份激励的三种表达"（RTL 复刻 PC 片段，模型是 RTL 的数值孪生），
  各写一套必然**静默分叉** —— 分叉后还"看着都对"，但比的是两段不同输入。
- **自我纠错轨迹**：
  - **我先试过只改 RTL** —— 这是错的：模型与 PC 生成端不改会立刻对不上，
    而且"对不上"的原因会被误判成 RTL 有 bug（与记录 3-2 同类的坑）。
  - 齐改三端后验证（用数字，不用眼睛）：
    - 仿真口径（320×180，12 帧）：`obj_x_at` 序列 `[40,56,…,216]`
      **与原公式 `x0+dx*t` 逐帧完全一致** → 回绕在仿真范围内**根本不触发**
      → 既有 11/11 **不该变**，实测**确实没变**（这条很关键：它证明改动没有偷偷改变已验证的行为）。
    - 板上口径（1280×720）：最右左边缘 **1116**、右边缘 **1276 ≤ 1280**（**永不出画**）；
      **第 67 帧回绕 ≈ 1.12 s @60fps**。
    - `make_test_clip` 默认 60 帧 → 回绕 **0 次** → 已产出的
      `synth_720p.avi / groundtruth / clipinfo` 的 SHA 不受影响，**不必重生成**。
  - **重跑完整闭环**：xsim 重跑（无 ERROR、X 检查干净）→ `rtl_golden.py --compare`
    → **共同帧 11 个，完全一致 11 个，不一致 0 个** ✅ → 重出 bit。
  - 已知副作用（**如实记，不说成"问题"**）：回绕那一帧帧差里"旧位置与新位置同时有白"，
    包围盒会**瞬间横跨大半个屏**（1 帧 ≈ 16 ms，肉眼基本看不到）。
    备选改法是"走到头反向（来回摆动）"—— **由用户定，不擅自改**。
- **相关 commit**：`82433ac`（`pattern_gen.v` 的源码即含回绕的 v2 版；v2 bit 见 `98706ee`）
- **是否 `#skill候选`**：✅ → `skill/video_pipeline_pitfalls/` 第 9 条

## 记录 4-3｜★ 工具坑：同一个文件在一轮里发多处编辑会**互相覆盖**

- **日期 / 编号**：2026-10-06 / 4-3
- **决策点**：改完三端要验什么？（这条是"验证方法"本身的纠错）
- **提示词**：`【要点复述】`（情境：同一轮里对 `pattern_gen.v` 发了 3 处修改、
  对 `make_test_clip.py` 发了 5 处修改，然后跑仿真）
- **模型回答**：（我自己的工具使用纪律）—— 报错给出了答案：
  `xvlog` 报 `VRFC 10-2989 'X_MAX16' is not declared`，
  说明新加的 `localparam X_MAX16` **根本没落进文件**；回头 Read 回读发现
  `pattern_gen.v` 只活了部分改动、`make_test_clip.py` 5 处只活了 2 处。
- **我做了什么判断**：**把结论写成硬规矩**：
  ① **同一个文件一次只发一处编辑**，改完**回读**；
  ② **工具返回 success ≠ 内容已落盘**。
- **自我纠错轨迹**：
  - 我最初以为"一轮里批量改同一个文件"更高效 —— **错了**，多处编辑互相覆盖，
    每处都返回成功，但文件里只保留了一部分。
  - **发现路径是靠编译报错反推的**：`X_MAX16 is not declared` 这个错
    **不可能是逻辑问题**（我刚加过这个常量），只能是"没写进去" → 于是 Read 回读，果然。
  - 修正：逐条重发，每次改完立刻 Read 回读确认，再跑仿真。
  - → 这条既是本项目的纪律，也已写进项目长期记忆（**同文件一次一处 Edit**）。
- **相关 commit**：`82433ac`
- **是否 `#skill候选`**：⬜ 属工具使用纪律，保留在 llm_log 与项目记忆中，**不单独建技能包**
