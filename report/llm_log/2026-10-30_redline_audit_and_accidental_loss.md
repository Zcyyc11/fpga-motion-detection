## 更严重的事故（我自己造成的）

补救时写的改名脚本有逻辑错误：

```
RENAME 循环只往 tree 里写了 sha: null（删旧中文路径）
但 collect() 只收 skill/report/board/data/sim/build
→ docs/ 下 35 份文档「删了旧名、没建新名」= 净丢失
```

**丢掉的包括设计报告成品。**

## 我是怎么发现的

不是靠 review 发现的，是**下游动作撞出来的**：

1. 想拉 `docs/design_report_final_20261029.docx` 解析章节 → API 回 **404**
2. 转去列 `docs/` 目录 → **只剩 1 个文件**（当天新建的 sync_notice）
3. 才回头查提交逻辑

**如果那天不去解析报告，这 35 份文档就一直躺在孤儿提交里没人知道。**

## 自我纠错轨迹

1. 立刻从 `d9173ce5` 取那 35 个中文路径的 blob sha
2. 按英文名重新挂 tree（**blob 复用，内容零改动**），提交 `bc61ff61`
3. 复核：260 文件、`docs/` 36 个、中文路径 0

## 两条铁律（新立）

1. **tree patch 里"删旧路径"必须与"建新路径"成对写入。** 更稳的做法是用 `git mv` 语义（新路径引用同 sha + 旧路径置 null）**在同一次提交里**完成，不要分两步。
2. **验证只数总数和中文数是不够的。** 当时"221 文件、中文 0"看着完全正常，实际是 88 + 133 的巧合，掩盖了 35 份文档的消失。**改名必须逐条核对新路径可访问。**

## 附带的一条工具坑

`git ls-tree` / `git ls-files` 默认对非 ASCII 路径做八进制转义（`"docs/\346\216..."` 全是 ASCII 字符），**直接 grep 非 ASCII 会误报 0 个**。必须加 `-c core.quotepath=false`。第一轮"仓库零中文"就是这么误判的。
