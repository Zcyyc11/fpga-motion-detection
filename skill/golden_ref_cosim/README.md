# Skill 3 · 黄金参考逐像素 / 逐字段比对脚本

## 适用范围

- **什么条件下能用**：任何"RTL 实现 ↔ Python 参考实现"需要**逐位对齐**的图像/信号处理项目；
  前置条件 = ① 能跑 xsim（或任何 Verilog 仿真器）；② **两侧使用同一套整数口径**
  （同样的取整、移位、边界处理、量纲）。
- **解决什么问题**：把"仿真看着像对的"升级为"**数字上证明是对的**"——
  给出逐帧逐字段的比对结论，而不是靠眼睛看波形或看导出图。

> 对应评分表「**功能正确与设计完整 20**」：官方不收纯仿真，但仿真必须是上板前的**过滤器**，
> 而过滤器的判据只能是数字。本技能就是把这条判据工程化。

## 使用方法

```bat
:: 1) 仿真侧：编译 + 仿真 + 导出 CSV（判成败看日志内容）
python build\scripts\run_sim.py

:: 2) 模型侧：生成参考表并与仿真 CSV 逐帧逐字段比对
python src\ps\rtl_golden.py --compare sim\wave\bbox_rtl.csv --report sim\logs\model_vs_rtl.txt

:: 3) 程序化体检导出图里的红框像素范围（"算出来了"还要证明"画出来了"）
python sim\view_sim.py
```

**必须两路对照，缺一不可**：

| 对照路 | 产物 | 判据 |
|---|---|---|
| **数字** | `sim/wave/bbox_rtl.csv`（`frame,valid,x1,y1,x2,y2,cnt`） | 与 `rtl_golden.py` **逐帧逐字段完全一致** |
| **画面** | `sim/wave/frame_*.ppm`（含红框） | 红框实测像素范围 == CSV 对应行 × 缩放系数 |
| **未知态** | `run_sim.py` 的 `x_hits` | 必须 = **0**（流水线里不能有 X） |

- **只对数字** → 不知道红框有没有真的画到画面上（"算出来了" ≠ "显示出来了"）
- **只看画面** → 差 2 个像素肉眼看不出来，会把 bug 当成功

- **关键参数说明**：`rtl_golden.py` 的默认参数（`w/h/obj_w/obj_h/x0/y0/dx/frames`）
  **必须与 `sim/tb/tb_md_pipeline.v` 一致**；两侧任何一侧改了整数口径，参照即失效。

## 已验证的效果

- **测试环境**：Vivado 2026.1 xsim；器件无关 RTL 12 个 `.v`；仿真尺寸 320×180（上板 1280×720，几何同比例）
- **结果**：
  - RTL vs Python 硬件模型 `src/ps/rtl_golden.py` → **共同帧 11 个，完全一致 11 个，不一致 0 个** ✅
  - 导出图红框位置 vs CSV bbox → **12/12 帧吻合**
  - `x_hits = 0`（无未知态）
  - 改过激励回绕规则后重跑，**结论不变（仍 11/11）** —— 说明该改动在仿真范围内确实不触发，与手算一致
- **证据文件**：`sim/logs/model_vs_rtl.txt`（报告原文含"共同帧 11 个，完全一致 11 个"）、
  `sim/wave/bbox_rtl.csv`、`sim/wave/sim_montage.png`、`sim/wave/sim_demo.mp4`

## 从哪些失败或观察中总结得出

1. **现象**：模型"前 6 帧对得上、第 7 帧起丢掉一条带"，看起来像 RTL 有 bug。
   **原因**：模型把数组写成了 `np.zeros((W, H))` —— 应为 `(H, W)`。
   RTL 的 `x` 是横向、`y` 是纵向，而 numpy 数组是 `(行=纵, 列=横)`，**两者互为转置**；
   写反不会报错，只会**静默裁掉**超出部分。**错的是模型，不是 RTL。**
   **结论**：numpy 形状按语义写 `(H, W)`；并在模型里加**激励自检**
   （白像素个数 + 左上角坐标），把这类静默错误顶到台面上。
2. **现象**：阈值 70 在模型里"行为不对"。
   **原因**：2×2 压缩用的是**求和**（`.sum()`，值域 0..1020），不是均值；
   写成 `.mean()` 量纲差 4 倍，阈值 70 就不是一回事了。
   **结论**：2×2 用 `.sum()`，并写清"阈值是**和域**阈值，≈单像素 17.5 灰阶"。
3. **现象**：逐帧比对报"末行/末列不一致"。
   **原因**：RTL 的形态学是**零扩展 + 居中锚点**，输出域是 `x∈[1,BW-2]`、`y∈[1,BH-2]`
   （窗口中心比右下角少 1，首/末行与首/末列不产出）；模型膨胀后没有把这一圈清零，
   于是多出 RTL 根本没有的像素。
   **结论**：软件模型必须**同步**做边界清零。
4. **现象（RTL 侧，最阴的一个）**：3×3 形态学的**第二级（膨胀）竖直方向静默失效** ——
   不报错、不报 X、波形也"正常"，只是结果偏小。
   **原因**：行相位原先用 `in_x == W-1` 触发；两级串联时第二级的 x 范围**永远够不到**该条件。
   **结论**：行缓冲类模块的相位**必须由数据流事件驱动**（改由 `row_start = in_y != py`，即"行号变化"），
   不能用"坐标等于某个值"驱动。**没有错误 ≠ 做对了。**
5. **观察**：`bbox` 用"全局并集框 + 面积门限"，不是 cv2 的最大连通域。
   **结论**：单目标时两者等价、多目标时不等价 —— 这是**已知取舍**，必须写进注释与报告，
   不能让它悄悄变成一个"看起来对但其实不同语义"的对照。

## 失效条件

- **整数口径必须逐条一致**：任一侧改了取整/移位/边界/量纲，对照立刻失效
  （表现为"处处不一致"，或只差 1 个像素这种难查的偏差）。
- **只做单目标验证** → **不能**用来证明多目标正确（bbox 语义差异）。
- **只做合成激励验证** → **不能**说明真实视频正确：本设计**没有 HDMI 输入通路**（灰度转换模块从未被实例化，已于 2026-10-06 移出仓库），
  真实视频从未进入这条链；因此本技能的结论边界是「**算法链在合成激励下逐位正确**」。
- **已知未覆盖的边界**：真实 HDMI 输入通路（TMDS 解码、时钟恢复）未纳入对照。
